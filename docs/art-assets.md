# 贴图资产产线规格（Art Asset Pipeline Spec）

> 状态：**产线工具与加载层已落地并验证；正式单位贴图尚未替换，人物造型概念已启动**
> 分支：`feat/asset-loader`（加载层）
> 适用范围：游戏内全部像素贴图（战斗单位、拾取物、投射物、天赋图标）
> 不适用范围：平衡数值、玩法规则、UI 布局

## 1. 目标

1. 把当前程序化绘制的战斗贴图重制为 **16×16 档**的真实像素资产，提升单位辨识度。
2. 为 34 个天赋补 16×16 图标，替代现行 emoji（emoji 保留为 fallback 与无障碍标签）。
3. 建立可复现的产线：**同一张图能用同一组参数重跑出来**，不依赖人工记忆。

非目标：不做动画帧、不做 8 方向朝向（除非后续单独立项）、不引入美术外包流程。

2026-10-31 人物美术专项已选定 C 布衣浪人，完成太刀左右两向、四种基础动作共 32 帧并接入。可见主体约 24 像素高，64×64 帧仅为刀尖 / 动作留透明空间；走独立职业渲染，不覆盖通用 `player` 清单。原始概念图不直接入游戏。详见 [人物美术升级：太刀样板](character-art-upgrade.md)，本文件其他早期资产规格仍按各节记录解读。

### 6.1 生成端硬性要求（与选哪个模型无关）

以下五条任何一条不满足，后处理都救不回来：

1. **直接输出目标网格**（16 / 24 / 48）。实测 64→16 即抹平 5×7 特征，1024→16 只会得到模糊色块。
2. **透明底**。
3. **可固定 seed**，便于复现与定向微调。
4. **可提供参考图**锁风格（现有程序化贴图导出 2× PNG 即可）。
5. **记录 model / prompt / seed 进 `assets/manifest.json`**。

补充：prompt 只描述主体，不写 "pixel art" 这类风格词；若模型有独立 style 参数，风格交给参数。

## 7. 后处理脚本规格（`scripts/pixelize.mjs`）

模型出图不能直接进游戏，必须过一遍确定性处理：

1. **解码**：读 8-bit PNG（支持 colorType 2/6，以及索引色 3）；16-bit 与交错格式直接报错，不静默转换。
2. **等比缩放**：按内容包围盒裁剪后等比缩放到恰好放入目标画布，采用**面积平均 + 预乘 alpha**。预乘是必须的——否则半透明边缘会把暗色吸进轮廓，产生脏边。**只缩不放**：源图小于目标时保持 1:1 居中，绝不放大插值。
3. **居中落位**：按整数偏移居中进目标画布，禁止半像素偏移。
4. **alpha 二值化**：`a < 128 → 0`，`a ≥ 128 → 255`。消除抗锯齿杂边，这是像素画能否干净的**决定项**。
5. **色板量化**：转到 Lab 空间取最近色（不用 RGB，避免暗部偏色），映射到第 4 节当前统一色板（29 色）。
6. **可选统一描边**：沿 alpha 边界四邻域外扩 1px `ink0`，用于消除模型间轮廓粗细差异。
7. **校验并输出**：唯一色数 ≤ 26、无半透明像素、尺寸等于规格表；任一不满足即退出码 1，不写半成品。
8. **落位**：`public/assets/sprites/<key>.png`，并把 `model / prompt / seed / 参数 / sha256` 追加进 `assets/manifest.json`。

依赖取舍：**已采用方案 B（零依赖手写 PNG 编解码）**，实现在 `scripts/lib/png.mjs`。理由：只处理贴图产线所需的子集（8-bit、非交错、colorType 2/3/6），不支持格式一律显式报错，风险可控；同时避免为一次性工具引入 `sharp` 这类原生依赖（原生模块会带来跨平台安装与 CI 复杂度）。

### 7.2 验证结果（2026-10-24，合成图探针）

用一张 64×64、带抗锯齿边、35 种非调色板色的合成图跑 `--key enemy_slime`：

| 检查项 | 结果 |
| --- | --- |
| 输出尺寸 | 64×64 → 16×16，符合规格 |
| 半透明像素 | 0 个（全部二值化） |
| 色数 | 35 → 3，全部落在调色板内 |
| 确定性 | 同输入重跑 sha256 完全一致 |
| 错误路径 | 未知 key / 尺寸冲突 / 非 PNG 均退出码 1 且报错清晰 |

**实测发现（重要）**：64×64 源图缩到 16×16 后，原本 5×7 像素的双眼被面积平均抹平，只剩下零星 1–2 个暗色像素。这说明**后处理无法救回在错误分辨率下生成的细节**——必须直接请求 16×16 网格生成，把大图缩小当保底手段是行不通的。这条从推测升级为实测结论，第 6.1 节第 1 条硬性要求的依据即在此。

## 8. 入库与加载（已实施，2026-10-24）

改动落在 `src/game/rendering/assetRegistry.ts`（新增）、`GameScene.ts`、`draw.ts`、`scripts/pixelize.mjs`。

| 改造点 | 改造前 | 现状 |
| --- | --- | --- |
| 贴图解析 | `draw.ts` 直接读 `SPR[key]` | 统一走 `spriteEntry(key)` → `{ tex, w, h }` |
| 纹理来源 | 仅程序化 Canvas | Canvas 兜底 + 外部 PNG 覆盖（纹理键 `ovr:<key>`） |
| 覆盖清单 | 无 | `public/assets/sprites/manifest.json`，由 `pixelize.mjs` 自动维护 |
| 玩家偏移 | 硬编码 `(x-4, y-5)` | 由贴图尺寸推导 `x - w/2, y - h/2` |
| 精英 | 固定 ×1.8 | 有 `elite_<spr>` 贴图时 1:1 绘制，否则沿用 ×1.8 |
| 回退 | 无 | 清单缺失或单张加载失败即回退程序化贴图，不阻塞启动 |
| 天赋图标 | `ico` emoji | 未改，仍是 emoji（第 5.3 节目标） |

关键设计取舍：

- **用 `fetch` + `Image`，不用 Phaser Loader**：清单本身决定加载哪些文件，走 Loader 需要两阶段加载，复杂度不划算。
- **覆盖而非替换**：Canvas 纹理始终先注册，PNG 加载成功后才覆盖解析表。因此**没有任何 PNG 时行为与改造前完全一致**，这是回归底线。
- **异步、失败不影响启动**：单张失败仅 DEV 下告警，保留程序化版本。

### 8.1 覆盖链路验证（2026-10-24）

用合成的 64×80 品红图跑 `--key player`（→16×20），在 e2e 模式实测：

| 检查项 | 结果 |
| --- | --- |
| 清单自动写入 | `{"sprites":{"slime":"slime.png","player":"player.png"}}` |
| 覆盖纹理注册 | `textures.exists("ovr:player")` = true，尺寸 16×20 |
| 兜底纹理仍在 | `textures.exists("player")` = true（Canvas 未被破坏） |
| 游戏内渲染 | 截图中玩家变为 16×20 品红方块，居中正确、无错位 |
| 页面异常 | 0 条 `pageerror` |
| 回归 | Vitest 40 项 + Playwright 6 项全过（含 production 构建产物） |

**过程中发现并修正的真实缺陷**：`plan.json` 原本用 `enemy_slime` 这类描述性键名，而运行时键是 `SPR` 的 `slime`。键名不匹配时覆盖**静默失效**——不报错、不告警，只是贴图不生效。现已统一为 `SPR` 键名，并在第 5.1 节写明命名硬约束。
