## 2. 八条实施约束（从代码读出来的，不是设计偏好）

### 2.1 属性必须作为「来源」参与重算，不能直接写字段

`recompute()` 的第一件事是 `Object.assign(this.player, statBase())`，然后重放 `picks` 序列、再 `applyTalentStatProjection`。

**所以任何直接写 `player.xxx` 的属性加点，都会在下一次重算时被静默抹掉。** 属性点必须存成「已选列表」，在重算里作为第二个投影重放——和 22 张已迁移的卡同一套机制。

### 2.2 投影必须幂等

已有前车之鉴：R-1（漏传 `potionMaxHpGrow` 导致 `maxHp` 静默按 0 重建）。属性投影同理——**修饰符数量必须由「已选属性点数组」逐步推出，不许维护累加缓存**，否则重算两次就叠两次。

### 2.3 影响上限的属性必须过 RuntimeState 快照

若属性包含生命上限、护盾容量、冲刺充能，重算后要经 `captureRuntimeState` → 重建 → `restoreRuntimeState` → `reconcileRuntimeToCaps`。「上限降低」方向要夹紧，反之不动。

### 2.4 可选字段不物化为 0

`recompute` 里有一张显式 `delete` 清单（`defense` / `resistances` / `globalDamageBonus` / `typeDamageBonus` / `formDamageBonus` / `skillDamageBonus`）。新增的可选属性键**必须加进这张表**，否则旧值会残留并叠加。

### 2.5 随机数纪律

`rollBoxPicks` 用 `hash01` 确定性伪随机，注释写明原因是「开箱可能发生在 parity 采集阶段」。天赋三选一用 `Math.random` 是安全的，因为它只在 UI 侧触发。

**属性选项生成也要留在 UI 侧。一旦挪进 tick，parity 的随机序列立刻分叉。**

### 2.6 天赋 `max` 改为 1 之后，宝箱会静默失效

`rollBoxPicks` 的条件是 `lv > 0 && lv < max`。天赋一次性获得后 `lv === max === 1`，**池子永远为空** → 每次开箱都走 Issue #71 兜底（转经验 + 血包）。

表现是「宝箱再也强化不了任何东西」，但**不会报错**。这是最容易漏的一条，必须在改 `max` 的同一批里处理宝箱逻辑。

### 2.7 卡名就是图鉴 id

`codex.syncTalents(upCounts)` 以名字为键。替换卡表会让旧条目变成孤儿。不是 bug，但要提前决定展示策略，否则玩家会看到「图鉴里有一堆再也不会出现的卡」。

### 2.8 新增的随机调用点会改变 parity 的随机序列

parity 的做法是把 `Math.random` 换成种子 LCG（`tests/parity.test.ts:297`、`seeded(900+wave)`），**基线 VM 与实时游戏用同一个种子**，所以两边的调用次数必须完全一致。

结论：**模拟里新增任何一次 `Math.random()` 调用，都会让后面的整条序列错位。** 法师的元素触发（「30% 概率触发闪电链」这类）如果写成 `Math.random() < 0.3`，一旦新卡进入 parity 的全天赋场景就会分叉。

**处理**：战斗内的概率判定优先用 `hash01(seed, counter)`（`CombatSystem.ts:204` 的宝箱掉落就是这么做的，注释写明「必须用 hash01，后者会推进随机序列」）。只有确认该分支在 parity 场景下不会被执行时，才允许 `Math.random`。

**关键路径 = B0 → B1 → B2 → B3 → B6 → B7。** 这条链上任何一环跳过，都会让后面的工作在错误的基线上做。

**为什么 B1、B2 必须在 B3 之前**：因为天赋表替换的前提是「旧表里那 15 张纯数值卡有地方可去」。属性系统就是那个地方。反过来做（先换卡表），那 15 张卡只能先删——而删了之后玩家会立刻掉一档强度，没有替代来源，第一版必然不可玩。

**状态容器的稳做法（按「最严谨」执行）**

| 要求 | 做法 | 为什么 |
|---|---|---|
| 固定形状 | 每个敌人一个 `status: { burn, chill, shock }`，三个子对象**显式全量初始化**（`{stacks:0, timers:[], ...}`），不用 `Map`、不用可选字段 | 避免隐藏类变化（项目有过性能历史问题）；也避免 §2.4 那类「可选字段没物化」的坑 |
| 单一入口 | `tickStatuses(dt)` 每帧推进一次，负责过期、层数衰减、反应结算 | 顺序确定 → parity 可复现；排查只有一处 |
| 单一写入点 | 只有 `applyStatus(e, kind, stacks)` 能改层数；卡牌逻辑调它，不直接碰结构 | 防止两张卡各自维护计时导致双层/漏删 |
| 概率用 hash01 | `hash01(e.seed, e.hitCount)` 而不是 `Math.random()` | 见 §2.8：新增随机调用点会错位整个 parity 序列 |
| 反应集中 | 三种反应（超载/融化/超导）写在同一张表里，由 `tickStatuses` 统一判定 | 避免「火雷在 A 卡判定、火冰在 B 卡判定」这种散落 |

## 5. 并行安全矩阵

**结论先行：只有「我方 / 怪物侧」这一条并行是安全的，其余全部串行。** 这是按「最严谨」裁的结果，理由在后面。

| 批次 | 可并行 | 不可并行 | 原因 |
|---|---|---|---|
| B0 | 怪物侧 | — | 只读 |
| B1 | 怪物侧 | — | `StatModel` 与怪物侧无交集 |
| B2 | 怪物侧 | B1（未完成时） | UI 依赖属性目录 |
| B3 | 怪物侧；熔炉关入口 | B4、B5 | 同时改 `TalentSystem` / 抽取逻辑会撞 |
| B4 | 怪物侧 | B5 | 串行（下方说明） |
| B5 | 怪物侧 | — | 串行 |
| B6 | — | B3–B5 未完成 | 退役名单依赖三池全定 |
| B7 | — | 怪物侧未落地 | 没有怪物数值就无法配平 |

**为什么 B4 与 B5 串行**（尽管拆文件后技术上可行）：

1. **抽取逻辑是共享的**。两个职业池会同时压测 `canOffer` 的过滤条件（前置/互斥/变体/流派），而这块只有一份实现——并行意味着两个人改同一个函数。
2. **回归判据互相污染**。B3 的验收项「一局 8 次天赋、单局可见 14 张」在 B4 落地后要重算一遍；并行时无法判断某次失败是哪个池引入的。
3. **单线程审查成本**。一个人 + AI 的配置下，并行省下的是编码时间，付出的是冲突解决 + 双份上下文切换，通常净值不为正。

**拆文件仍然建议做**，但理由改成「降低单文件复杂度 + 让每个职业的卡表可独立 review」，**不再是为了并行**。645 行的表里塞三个职业，改一张卡要在千行里找位置，这个成本是实打实的。

## 6. 最小可行切片（第一个能玩的版本）

**B0 → B1 → B2 → B3**。四批做完就能得到：

**风险验证的覆盖率**：八条实施约束里，2.1/2.2/2.5/2.6 全部会在切片里暴露。剩下的（2.8 随机序列、元素状态、开局流派、配平）留给 B4–B7。

**不建议先做 B7（配平）**。配平在机制不定时做，等于给一个还会变形的骨架量体裁衣——上一轮返工就是这么来的。

## 7. 验收基线与 parity 策略

这是最容易违规的一处，单独列。

**三阶段策略**：

| 阶段 | 涉及批次 | parity 要求 |
|---|---|---|
| 一 · 行为零变化 | B1、B2 | **必须全绿，不许加排除**。属性点为空、无选择时，模拟必须逐 tick 一致 |
| 二 · 新卡隐藏 | B3–B5 | 仍全绿。旧卡 `hidden` 而非删除，`UPGRADES` 里仍在，逐字段对照继续成立 |
| 三 · 旧卡退役 | B6 | 走 `BASELINE_EXCLUDED` / `NOT_IN_V8` 扩展，**不删测试段**；为新表补显式公式断言 |

**第三阶段的具体做法**（按项目既有规矩）：

1. 「41 张逐字段对照」那段**保留结构**，把退役的卡加进排除名单，其余不动；
2. 为每条新链写显式断言：伤害期望、触发率、层数上限可达性（先确认独立计时还是整体刷新，规则 §4.2）、互斥互不出现在同一次三选一；
3. 提交信息写明「基线更新依据：Issue #X」，`docs/migration.md` 登记；
4. **配一次变异验证**：故意改错一个系数，确认新断言会红。

> 为什么强调「不删段」：删除断言等于让未来的自己失去判断力。排除名单至少还保留了「这些卡曾经被逐字段验证过」的事实。
