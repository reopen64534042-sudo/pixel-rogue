## 2. 六条实施约束（出错会静默，压缩不得）

### 2.1 属性必须作为「来源」参与重算

`recompute()` 第一件事是 `Object.assign(player, statBase())`，然后重放 `picks`、再 `applyTalentStatProjection`。

- **直接写 `player.xxx` 的属性加点，下一次重算就没**，且不报错。必须存成「已选列表」，在重算里作为第二次投影重放。
- **投影必须幂等**：修饰符数量由数组逐步推出，不许维护累加缓存（前车之鉴 R-1：漏传 `potionMaxHpGrow` 导致 `maxHp` 静默按 0 重建）。
- **影响上限的属性要过 RuntimeState**：`captureRuntimeState` → 重建 → `restoreRuntimeState` → `reconcileRuntimeToCaps`，只在「上限降低」方向夹紧。

### 2.2 可选属性键必须进 `recompute` 的 delete 清单

现有清单：`defense` / `resistances` / `globalDamageBonus` / `typeDamageBonus` / `formDamageBonus` / `skillDamageBonus`。新键不加进去，旧值会残留并叠加。

### 2.3 随机数纪律

parity 用种子 LCG 替换 `Math.random`（`parity.test.ts:297`），**基线 VM 与实时游戏共用同一序列**——所以模拟里新增任何一次 `Math.random()` 都会让后面整条序列错位。

- **选择类随机**（天赋/属性选项）留在 UI 侧，用 `Math.random` 安全；
- **战斗内概率**（元素触发、闪避）用 `hash01(seed, counter)`，见 `CombatSystem.ts:204` 的宝箱掉落（注释写明「必须用 hash01」）。

### 2.4 天赋 `max` 改成 1 之后，宝箱会静默失效

`rollBoxPicks` 的条件是 `lv > 0 && lv < max`。`max = 1` 后恒假 → **池子永远为空** → 每次开箱走 Issue #71 兜底（转经验+血包）。表现是「宝箱再也强化不了任何东西」，**不报错**。必须与 `max` 改造同批处理。

### 2.5 卡名就是图鉴 id

`codex.syncTalents(upCounts)` 以名字为键，替换卡表会让旧条目变孤儿。要提前定展示策略。

### 2.6 层数上限取决于计时方式

`可达层数 = 攻速 × 维持` **只适用于独立计时**；整体刷新（战士「流」）下只要命中间隔小于维持时间就能一直叠。两种算法混用会得出「上限不可达」的错误结论（规则 §4.2）。

## 3. 四个阶段

```
S1 属性系统 ──► S2 射手纵切（第一个可玩版）──► S3 法师 + 战士 ──► S4 清场与配平
   底座+发放         链/变体/互斥/节点发放        串行两个里程碑      旧卡退役→配平→收尾
        │                                                                  ▲
        └──────────────── 怪物侧数值（协作者，独立 worktree）──────────────┘
                                    全程并行，只在 S4 交汇
```

| 阶段 | 一句话 | 内部检查点 | 关键路径 |
|---|---|---|---|
| **S1** 属性系统 | 属性加点成为合法来源，且波末能选 | 2 个 | ✅ 必经 |
| **S2** 射手纵切 | 第一个能从头玩到死的版本 | 3 个 | ✅ 必经 |
| **S3** 法师 + 战士 | 另外两套门控跑通 | 4 个（各 2） | ✅ 必经 |
| **S4** 清场与配平 | 旧卡真退役、数值对上 | 3 个 | ✅ 必经，**等怪物侧** |

**为什么不能再压成三个**：S4 必须等怪物侧落地，物理上无法提前；S2 是三职业里唯一能自证的样本（池子结构、抽取、发放全都在它身上第一次跑），砍掉它会让 S3 一次面对三倍未知。

## 5. 并行

**只有「我方 / 怪物侧」这一条并行是安全的**，S1–S4 内部全部串行。

| 谁 | 能同时做什么 | 不能 |
|---|---|---|
| 我方 | S1 → S2 → S3a → S3b → S4 顺序推进；期间可插入「熔炉关入口」（独立、可逆） | 三职业并行 |
| 协作者 | 怪物数值 / 生成 / AI，独立 worktree，全程可并行 | 碰 `talents.ts`、`TalentSystem.ts` |

**为什么职业之间不并行**：抽取逻辑只有一份实现（`canOffer` 的前置/互斥/变体/流派过滤），并行等于两人改同一函数；回归判据互相污染（「8 次天赋、可见 14 张」在下一个池落地后要重算，并行时分不清责任）；单人 + AI 下省的是编码时间，付出的是冲突与归因成本，净值为负。

拆文件仍然做，但**理由改成「让每张卡表能独立 review」**，不再是为了并行。

**S1 → S2**。做完就有一个能从头玩到死的版本：选职业、每波加属性（四选一 + 刷新 + 稀有度）、精英给天赋（一局 8 次）、射手 18 张完整链。

## 7. 验收基线与 parity

| 阶段 | parity 要求 |
|---|---|
| S1 | **必须全绿，不许加排除**。属性点为空时模拟必须逐 tick 一致 |
| S2–S3 | 仍全绿。旧卡 `hidden` 而非删除，逐字段对照继续成立 |
| S4 | 扩展排除名单，**不删测试段**；为新表补显式公式断言；配一次变异验证 |

> 为什么不删段：删除断言等于让未来的自己失去判断力。排除名单至少保留了「这些卡曾经被逐字段验证过」的事实。
